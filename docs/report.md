# Практическая работа № 2. Построение пайплайна пакетной аналитики

## Тема и цель работы

Реализовать ELT-пайплайн для публичных событий GitHub: получить реальные файлы, загрузить их в объектное хранилище, после загрузки подготовить аналитические данные и выполнить запросы.

## Постановка задачи

По условию нужен датасет не менее 500 МБ, сжатый исходный слой, обоснованное преобразование для аналитики и демонстрация запросов. В проекте задан более строгий порог — 550 MiB сжатых JSON.GZ. Полная проверка и небольшой smoke-запуск разделены.

## Используемые технологии

Java 17 Eclipse Temurin, Gradle Wrapper 8.14.4, Apache Spark 3.5.8 (Scala 2.12), Hadoop 3.3.4, hadoop-aws 3.3.4, AWS SDK bundle 1.12.262, MinIO RELEASE.2025-04-22T22-12-26Z, Docker Compose, JUnit 5.11.4. Java-версия проверяется приложением и скриптами. Spark и Hadoop предоставляет фиксированный Docker-образ, дополнительные S3A-зависимости добавлены при сборке.

Версии выбраны по [POM Spark](https://github.com/apache/spark/blob/v3.5.8/pom.xml) и [POM Hadoop](https://github.com/apache/hadoop/blob/rel/release-3.3.4/hadoop-project/pom.xml), а не независимо друг от друга.

## Описание исходных данных

Источник — [GH Archive](https://www.gharchive.org/). Файлы содержат публичную активность GitHub: PushEvent, PullRequestEvent, IssuesEvent, WatchEvent и другие события. Формат — по одной JSON-записи в строке, файл сжат GZIP. Исторический диапазон начинается 1 октября 2024 года в 00:00 UTC. Загрузчик получает последующие полные часы до заданного объёма, без искусственного размножения записей. Точный интервал, размеры и SHA-256 сохраняются в манифесте.

## Архитектура ELT

GH Archive → локальный `data/raw` → MinIO bucket `raw` → Spark через S3A → MinIO bucket `curated` → Spark SQL → `analytics` и локальный `results`.

В Extract не выполняется аналитическая обработка. Load сохраняет оригинальные JSON.GZ. Только Transform разбирает JSON, очищает и типизирует данные. Это и определяет порядок ELT. MinIO сохраняет данные в именованном Docker volume.

## Реализация Extract

`DatasetDownloader` формирует имена почасовых архивов в UTC и скачивает их через Java HttpClient. Незавершённый файл имеет расширение `.part`. Перед переименованием файл полностью распаковывается в пустой поток, поэтому проверяются заголовок, структура GZIP и CRC. SHA-256 и размер записываются в `manifest.tsv` после каждого часа. При повторном запуске корректные архивы используются снова. На сетевые ошибки предусмотрены четыре попытки. Диапазон ограничен параметром MAX_HOURS; если объёма не хватает, программа завершается с понятной ошибкой.

## Реализация Load

`RawDataLoader` использует S3 SDK с endpoint MinIO, path-style адресацией и повторными сетевыми запросами. Перед загрузкой проверяется SHA-256 локального файла. В metadata объекта сохраняются контрольная сумма и URL источника. Существующие объекты с теми же размером и SHA-256 пропускаются. После загрузки проверяется наличие и metadata каждого объекта текущего манифеста. Исходные данные сохраняются без изменения. Bucket `raw`, `curated`, `analytics` создаются сервисом minio-init через тот же Java SDK.

## Реализация Transform

Spark Job выполняется через spark-submit в standalone-кластере из Master и Worker. Явная схема читает ID и тип события, пользователя, репозиторий и время. Большой неоднородный payload не раскрывается. Из вложенных структур получается таблица с десятью полями. Timestamp и дата рассчитываются в UTC, час — 0…23, день недели — 1…7 с понедельника.

Удаляются повреждённые JSON и записи без ID, типа или корректного времени. Пропуски пользователя/репозитория допустимы. Дубликаты удаляются по event_id. Статистика отдельно показывает входные строки, повреждённые, невалидные, повторные и итоговые события. Временная persistence на диске исключает многократный разбор JSON при сборе этих показателей; перед benchmark она снимается.

Результат сохраняется в Parquet Snappy с разделением по event_date. Четыре раздела записи ограничивают количество файлов несколькими файлами на день для выбранного небольшого диапазона. Повторное чтение из MinIO проверяет схему, число строк и уникальность ID.

## Обоснование аналитического формата Parquet

JSON удобен для обмена вложенными данными, но для каждого запроса приходится читать и разбирать текст. GZIP уменьшает размер, однако отдельный архив не разделяется Spark на независимые диапазоны чтения.

Parquet хранит значения по столбцам с типами и статистикой. Spark читает только необходимые столбцы, а фильтр даты исключает ненужные разделы. Snappy ориентирован на скорость сжатия и распаковки. Подготовленные типы позволяют группировать даты и часы без повторного разбора времени. Это делает повторную аналитику проще и потенциально быстрее.

Разница размеров отражает не только формат: из curated также исключён payload. Поэтому уменьшение нельзя целиком приписать Parquet или Snappy. Размер JSON.GZ сравнивается именно со сжатыми Parquet-файлами; служебные marker и checksum объекты в размер Parquet не входят.

## Выполнение аналитических запросов

Реализованы шесть запросов Spark SQL: распределение по типам событий; активность по часам UTC; динамика по дням; Top-20 репозиториев; число уникальных пользователей и репозиториев по ID; распределение типов событий по дням. Запросы читают только curated в MinIO. Результаты выводятся таблицами, сохраняются в JSON Lines локально и CSV в analytics bucket.

Пример:

```sql
SELECT repo_name, count(*) AS events
FROM events WHERE repo_name IS NOT NULL
GROUP BY repo_name ORDER BY events DESC, repo_name LIMIT 20;
```

NULL исключается из счётчиков уникальных ID. Репозитории в Top группируются по имени; переименования могут разделить историю.

## Сравнение размеров и производительности

Benchmark использует распределение типов и Top-20 репозиториев с одним фильтром по первому дню. RAW очищается и дедуплицируется по тем же правилам, что curated. Результаты двух вариантов сравниваются на равенство. Выполняются прогрев и три измерения, порядок форматов чередуется. Измеряется настоящее выполнение через collectAsList, включая построение плана, чтение и агрегацию; итоговый показатель — медиана.

Spark cache сбрасывается перед каждым измерением. Кеш ОС и MinIO остаётся, поэтому измерения относятся к тёплому локальному запуску. Стоимость подготовки Parquet не включена в его SQL-запрос; RAW выполняет очистку каждый раз. Планы запросов сохраняются отдельно. Если весь диапазон относится к одной дате, partition pruning не уменьшает число читаемых дат, хотя выбор столбцов остаётся полезным.

В полном запуске RAW JSON.GZ занял 659 811 286 байт (629,25 MiB), Parquet — 76 248 854 байта (72,72 MiB). Получилось четыре Parquet-файла на одну дату. Отношение размеров — около 8,65; Parquet занимает около 11,56% размера RAW. Это результат выбранной плоской схемы, очистки и колоночного формата вместе, а не сравнение двух форматов с одинаковым полным payload.

Первый полный запуск завершён в 13:02:06 UTC. Повторная обработка полного RAW после перезапуска контейнеров завершена в **13:07:35 UTC 09.10.2026** на окончательной версии проверок. Для следующих таблиц использован именно повторный запуск.

## Проверка корректности

Модульные тесты проверяют UTC-имена архивов, обнаружение повреждённого GZIP, SHA-256, медиану, продолжение загрузки из готовых архивов и ошибку недостаточного диапазона. Интеграционная фикстура Spark проверяет очистку, пропуски, дубликаты и вычисляемые поля. Эта небольшая фикстура используется только как тест, а не как источник лабораторного датасета.

Полный пайплайн проверяет порог RAW в MinIO, существование и metadata объектов, чтение Spark, непустой результат, типы и критические поля, отсутствие дубликатов и повторное чтение Parquet. Суммы распределений должны совпадать с числом curated-событий, счётчики уникальных объектов не должны превышать это число, Top ограничен двадцатью строками. Сохранённые CSV повторно читаются из analytics bucket с проверкой заголовков и числа строк. RAW и Parquet в benchmark должны давать одинаковый результат.

Планы полного benchmark подтверждают выбор столбцов: запрос типов читает `ReadSchema: struct<event_type:string>`, Top-20 читает `struct<repo_name:string>`. `event_date` используется как PartitionFilter. В этом наборе только одна дата, поэтому фактическое ускорение не является доказательством выигрыша от отбрасывания других дней.

Возникшие проблемы и решения:

1. Java 17 установлена в `.jdks`, но отсутствует в PATH. Скрипты находят Temurin 17 и задают JAVA_HOME для своего процесса.
2. Windows PowerShell 5.1 неверно прочитал UTF-8 без BOM. Скрипты сохранены с BOM; документация и Java остаются UTF-8.
3. Загрузка MinIO сначала завершалась TLS timeout, затем Docker Hub возвращал pull access denied, официальный Quay — 401, архив бинарников — HTTP 410. MinIO собирается из официального исходного commit выпуска, без изменения его кода. Go 1.24.2 используется только в build stage.
4. HTTPS с Windows к GH Archive завершался handshake_failure; тот же официальный URL доступен внутри Linux-контейнера. Основной run.ps1 скачивает данные внутри Docker с включённой проверкой TLS; источник не заменён.
5. Master слушает порт 7077 на адресе spark-master, поэтому healthcheck на localhost давал ложную ошибку. Проверка перенесена на адрес spark-master; после регистрации Worker задачи начали выполняться.
6. PowerShell Transcript первоначально не сохранял вывод нативных команд в этом режиме терминала. Обёртка теперь переводит оба потока в текст, пишет их в журнал и отдельно проверяет exit code. На повторном запуске весь вывод Spark и benchmark сохранён в `logs/job-pipeline-full-20261009-160601.log`.

Предупреждения Spark о native-hadoop library и metrics properties не помешали выполнению: используются Java-реализации Hadoop. Стандартный FileOutputCommitter также выдаёт предупреждение при работе с S3A. В этой лабораторной используется один последовательный писатель, после записи результаты перечитываются. Атомарная публикация новой версии набора и восстановление прерванной записи без повторного Transform не реализованы; при прерывании нужно повторить pipeline.

Ограничения проверки: не проводилось тестирование на другом компьютере, длительное нагрузочное тестирование или сравнение холодного диска. Принудительное обрывание сети при большой загрузке не проверялось; реальные сетевые ошибки при первом обращении вызвали предусмотренные повторные попытки и ненулевой код завершения. Проверка недостаточного диапазона, повреждённого GZIP и продолжения готовых файлов покрыта модульными тестами. Разделение по датам реализовано и видно в плане, но многодневное отбрасывание разделов не измерялось.

Выполнен настоящий ELT-пайплайн на 629,25 MiB сжатых данных GH Archive. Исходные архивы загружены в MinIO до аналитического преобразования, Spark обработал 1 532 870 событий и записал Parquet обратно в хранилище. Выполнены шесть SQL-запросов; суммы агрегатов и повторное чтение CSV проверены. В двух выбранных сценариях подготовленный Parquet оказался быстрее исходных JSON.GZ. Сохранность данных после остановки контейнеров и отсутствие повторной отправки идентичных RAW подтверждены реальным запуском.
